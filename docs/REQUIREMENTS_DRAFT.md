# Candidate product requirements

> **Docket (formerly Task Lite).** This draft is history: it keeps the name the product had when it was written.

Status: discovery draft, updated 2026-11-07. **Superseded as the requirements of record by [specs/001-task-lite-v1/spec.md](../specs/001-task-lite-v1/spec.md), and for building by [BUILD_SPEC.md](BUILD_SPEC.md), [MCP_SPEC.md](MCP_SPEC.md) and [UI_SPEC.md](UI_SPEC.md);** this file remains the record of owner decisions and the original requirement IDs those documents cite. The confirmed choices below are owner decisions; remaining requirements are proposals to test with real agents. Background: [Jira capability research](JIRA_RESEARCH.md).

## Confirmed owner decisions

1. Build and verify MVP V1 before selecting a pilot project. Then pilot one project before any broader Jira replacement. No pilot project is selected yet; active projects stay on Jira during their current work.
2. Codex and Orca workers must connect on day one. Claude must also be supported. Use the already installed agent clients; do not require this service to call model APIs or launch new model instances.
3. Subagent steps do not need separate work items. A ticket must show what the lead agent plans to do, what is underway, what is complete, and what subagents contributed. A short attributed subagent log entry is sufficient when detailed session telemetry is unavailable.
4. Review documents and Markdown artifacts live in local project-associated storage managed by the service. Git publication happens only when the actual project's workflow explicitly calls for it.
5. Approval gates vary by project and its agent workflow. Some projects require explicit owner approval at defined points; others allow an agent to finish and report completion without an owner gate.
6. Human and agents may enter or change planned dates. Effort values and velocity-based backlog forecasts are desirable planning additions; forecasts must be distinguished from entered dates.
7. The V1 browser UI is available on the host machine only. Other-device or public access is outside the V1 boundary; this public repository should keep local-only networking as its default.
8. The workflow includes a **Planning** status between Inbox and Ready. Planning is the owner's stage: planning artifacts (for example UI/UX design, PRD, TDD) are produced there, and the owner moves an item to Ready, or tells an agent to, when it is actually ready to build. (Added 2026-11-06.)
9. Ceremony should fit the risk. Which planning artifacts a ticket needs is settled during Planning and by each project's agent workflow; small changes may skip UX/TDD, and high-stakes production work may require all of them. (Added 2026-11-06; revised the same day.)
10. The browser UI starts at an all-projects view on each visit, so the owner is never unknowingly scoped to a single project. (Added 2026-11-06.)
11. Per-item planning exceptions and readiness rules are decided by each project's agent constitution and workflow. The tracker stores and shows the project's configuration and records deviations; it does not enforce them. (Added 2026-11-06.)
12. V1 item types are Epic (the only container), Story, Task, and Bug. An Epic still in Planning acts as the brief for work not yet broken down. Large initiatives that span several epics use a label with an optional brief rather than a level above Epic. Small steps are checklist items on the ticket; subtasks are not in V1. (Added 2026-11-06; revised the same day.)
13. Human review is verification after implementation, not part of Planning. Agents declare human review items on a ticket, usually during Planning. When the work is built and the agent's own checks pass, the agent supplies a handoff packet telling the owner how to verify. The owner approves (the ticket closes) or requests changes (each finding becomes a checklist item or a new bug ticket, and the agent prepares another round). A ticket cannot close while any human review item is undecided; with no human review items, the agent may close it once its checks pass. The owner may also **defer** an item: this clears the gate but records the item as deferred, not verified, optionally creating a follow-up test ticket. Packets record the commit they were built from and are marked out of date automatically when an agent later reports a different commit for the ticket. Approvals carry forward across rounds. Agents may create labels. Commits are reported for a specific ticket, so only commits for that ticket (or, for an epic-level packet, any ticket in the epic) mark a packet out of date. When an epic ships as one PR, human review may be declared once on the epic instead of on each child. Deferred, not-verified items stay visible to the owner and to agents (for cleanup) until resolved. (Added 2026-11-06.)

14. The V1 stack is TypeScript end to end: Node 22, the official MCP TypeScript SDK, Hono, SQLite via better-sqlite3 + Drizzle, and React + Vite for the UI. (Added 2026-11-07.)
15. O11's project-level approval policies are superseded by decision 13. Gates are per-ticket human review items, declared according to each project's agent workflow; the tracker enforces only that a ticket can't close while a review item is undecided. H06 reads "a ticket with human review items" where it says "a project with a required owner gate". (Added 2026-11-07.)
16. One agent bearer token serves all clients. The calling client is identified from the MCP handshake (`clientInfo`), plus an optional agent label such as `orca-w3`. A separate owner key, held only by the browser, protects owner actions. (Added 2026-11-07.)
17. V1 also includes four P1 items: the Timeline layout, Label pages, burn-down and forecast (H14, A18), and the Jira import dry run and import (O05). (Added 2026-11-07.)
18. Task Lite is the coordinator, not the dispatcher. It is the authoritative record of what work exists, what is eligible to start, who holds it, and the rules (blocking, leases, review gates), and it enforces them. Orca, or the owner, decides when to start agents (decision 2 reaffirmed after the 2026-11-14 "development control plane" review). Revisit after the pilot. (Added 2026-11-14.)
19. V1 adds four coordination features from that review: a context bundle for agents (`get_context`), decision records that every agent reads (owner records are authoritative), lean agent responses (summary views, field selection, compact text, token budgets), and stricter dependency rules (a blocker can be required to be merged or verified, not just done). (Added 2026-11-14.)
20. TERSL / Tourbillon is a reference to learn from, not a dependency. No TERSL format or TERSL/DB in V1; the learnings applied, and an optional post-V1 experiment, are in [ROADMAP.md](ROADMAP.md). (Added 2026-11-14.)
21. Opt-in desktop notifications in the browser for new "for you" events only (handoff ready, question asked), plus the for-you count in the tab title. Nothing leaves the machine. (Added 2026-11-14, spec clarification.)
22. The owner can edit an item's title, description, outcome and acceptance criteria inline in the UI. Planned dates, effort and blocker links stay agent-edited in V1. (Added 2026-11-14, spec clarification.)
23. The owner can cancel any open item from the UI, with an optional reason and Undo. (Added 2026-11-14, spec clarification.)
24. Nightly backups stay in the service's data volume by default; the owner can opt in to an extra copy in a folder on the host machine. (Added 2026-11-14, spec clarification.)
25. The browser UI requires the owner key to unlock, once per browser, with a 30-day session from last use; the owner can lock a browser or rotate the key. (Confirmed 2026-11-14, spec clarification.)
26. Recovery support: runs record where their work lives, the orchestrator's IDs, their brief and the resources they start; runs can park while waiting on purpose; a restart list lets a coordinator re-dispatch interrupted work without guessing; the owner sees orphaned resources and unpushed work at risk. Task Lite records; the coordinator acts. Prompted by an Orca crash that pruned worktrees holding in-flight work. (Added 2026-11-15.)
27. Agent skills ship with Task Lite as plain files in `skills/`, so the owner can hand them to Orca or any agent and edit them to fit their own tooling: two core (`tasklite-worker`, `tasklite-coordinator`) and three optional (`tasklite-planner`, `tasklite-review-packet`, `tasklite-lead-subagents`). Not served over MCP in V1. (Added 2026-11-15.)
29. Help and agent setup inside Task Lite (2026-11-17). A **Help** area of short how-to articles for the owner, with contextual links from each screen. An **Agent setup** area where the owner views, edits and installs the agent files Task Lite ships (the skills and the AGENTS.md block), in three layers: bundled, service-wide edits, and per-project overrides, because projects may run their own workflow tools (for example Spec Kit) and need tailored skills. Each project also gets **Workflow** notes delivered to agents in `get_context`. Install by a copy-paste command, or by an opt-in push into a host folder the owner mounts. Every install is logged with the exact file versions, and Task Lite can show when installed copies were edited locally, so the owner can tell whether bad instructions caused a problem. Serving the files over MCP stays on the roadmap. (Decision 28 is the per-client result mode in BUILD_SPEC.)
30. Agents may change agent files only by proposing, and the owner approves (2026-11-18). Agents read the current agent files and Workflow notes through MCP and propose a change with a reason. The owner approves, edits then approves, or declines, and history records who proposed and who approved. Because people and agents will still edit installed files directly (in VS Code, Orca or a terminal), Task Lite also **detects drift**: it checks installed copies in the push folder on a schedule, and agents report the hashes of the instruction files they actually have when they claim work. A drifted file shows up for the owner with a diff and three remedies: adopt it as the project's copy, restore Task Lite's version, or keep the local version on purpose. Each run records which instruction versions it worked from.
31. Onboarding a project, with nothing installed first (2026-11-18). The owner can create a project in Settings (*New project*). Any connected agent can onboard a repo through MCP: `onboard_project` creates the project, or adopts an existing one (for example, right after a Jira import), and returns the onboarding guide in its result, so no skills need installing first. The same guide is offered as the first MCP prompt for clients that support prompts. The agent surveys the repo's planning sources (Spec Kit specs, plans and tasks, issues, TODOs, docs), reconciles them with items already in the project (matching Jira keys and titles, enriching rather than duplicating), creates everything in Planning, proposes Workflow notes, and calls `finish_onboarding` with a summary. The owner reviews from one Needs you card, which also offers installing the agent files. Agents can create and fill projects but can't change a project's settings or delete it. Prompted by the Gameflow pilot (GitHub code, Spec Kit planning, Jira tickets).
32. Local trust by default (2026-11-18). Docket runs on the owner's machine, so the owner unlock and the agent token were extra steps without much real protection: an agent with a shell can read the owner key anyway. By default there's no unlock and no agent token; the Host and Origin guards stay, so websites and other machines still can't reach it, and every owner action records whether a browser or a script made it. An opt-in **protected mode** restores the owner session and the token. Connecting agents needs no commands: the agent-files install also writes each client's project connection file (`.mcp.json` for Claude Code, `.codex/config.toml` for Codex), which contain no secret, and the client asks once to approve or trust it. Supersedes the parts of decisions 16 and T2 that required a token and an owner key by default.
33. Checklist steps carry details (2026-11-18). A work step keeps its ID, title, status and history, and gains optional **details** (Markdown) and a **source** (for example a Jira key). The owner reads and edits a step in a **step dialog** (not an inline accordion), which shows the title, status, source, details, history and subagent notes, with previous and next. Agents read details on demand, so ordinary reads stay small. The Jira import turns each sub-task into a step on its parent with its full description in details and a header line for assignee, dates and points, and collates all the sub-tasks' comments into one note on the parent. Prompted by the Gameflow pilot, where sub-tasks carry real descriptions.
34. Install and onboarding follow-ups from the Gameflow pilot (2026-11-19). The standing rule: agents do every step an agent can do. (1) One install writes several clients: the Install dialog offers Claude Code and Codex as checkboxes, ticks the clients the repo already shows signs of (`.claude/`, `.codex/`, `.agents/`, `CLAUDE.md`, `AGENTS.md`), or both, and shows one summary of each client's files; the bundle, push install, copy-paste command and owner API all take several clients, and the single-client form keeps working. (2) The dialog and Agent files show each client's install state: up to date (*Check*, *Reinstall*), update available (*Update*), changed outside Docket (*Review changes*) or not installed (*Install*), worked out from the latest install's manifest and the drift checks, with nothing new stored; an installed client is never offered a plain *Install*. (3) When a repo has `AGENTS.md` but no `CLAUDE.md`, the install creates `CLAUDE.md` starting with `@AGENTS.md`, outside the Docket markers, so Claude agents also read the project's own rules; an existing `CLAUDE.md` never gets the line. (4) Agents can batch writes: `apply_batch` takes up to 100 operations (creates, enrichments, links, documents, step details, decisions), each checked like its single call and applied on its own, so one session can onboard a large repo; the onboarding guide and the planner skill use it. (5) Agents may add details to steps imported from Jira (set or extend, never rewrite), recorded as "details added by <agent>"; their text stays the owner's, and owner-typed steps stay fully protected. Prompted by the Gameflow onboarding (305 matches, 44 enrichments, 39 documents), which needed a script on a second connection.
35. Approve with notes (2026-11-19). Reviewing GF-312 in the Gameflow pilot, the owner wanted to mark a finding *Looks good* (the ticket does everything it needs to) and still leave notes, so that agents implementing **later** tickets know those things. *Looks good* now takes an optional note, and where to keep it: **this ticket** (the default), **the epic's future tickets** or **all of the project's work**. The note is always stored on the verdict, posted to the item's agent as an owner note ("Approved with a note: …"), and shown in the packet's round history and the item's Activity. Kept for the epic or the project, it also becomes an **owner decision** in that scope (the title from the note, the note as the decision, and "From your review of <ITEM>, round <n>: <finding>" as the rationale), which is how it reaches agents on future tickets: decisions in scope already arrive through `get_context` and `get_item`. It's created with the verdict, so Undo reverts both. Without an epic, the epic choice is disabled. *Needs changes* and *Defer* are unchanged.
36. Shared changes and conflict guardrails (2026-11-20). In the Gameflow pilot, independent epics (accounts, sharing, figures, tokens) all change the same APIs, models and database. Bundling their infrastructure into one up-front wave made the most advanced epic wait on epics with no design yet, and letting them run in parallel produced merge conflicts. Work runs unattended overnight, so guardrails must be enforced by Docket, not left to agents' judgement. Each item declares the **shared parts** it will change (a table, model, endpoint, shared file, or none) before it can be Ready. **Claiming an item whose shared parts overlap another in-flight item's is refused**, and the owner gets a question to sequence the two or confirm they're compatible, so conflicting work waits instead of starting. **Single-writer parts** (such as an EF migration snapshot) are taken with a short **lease**. At hand-off, files changed outside the declared parts stop the item for review. A **conflict radar** trial-merges in-flight branches and warns before two items collide. Agents see other in-flight items' declared changes in their context, so they plan against main plus work in flight. Worst case overnight: work pauses with a question; it never lands in a tangle.
37. Problems that say what's wrong, who fixes it and what to do (2026-11-20). In the Gameflow pilot, Needs you showed 13 Problems, all conflict-radar findings, and *Open* went to a ticket that said nothing about the problem. The owner couldn't tell what was wrong, whether a decision was needed, or what to do next. None needed the owner: 4 stale epic branches were far behind main, most of the 13 were knock-on pairs from those 4, and the agents fixed them by clearing archival branches. So **every problem says three things in plain words: what's wrong, what fixes it, and who acts** (an agent, or you), written once by the server so agents and the owner read the same words. **Agent problems** (radar findings, out-of-date branches) go first to the leads of the items involved, in their context and as one note on the item; they reach the owner only when nobody leads the item or they're still open after a grace period (a day by default), and the card says why. **Owner decisions** (overlaps, undeclared holds) stay immediate. Needs you says how many problems agents are handling, so nothing is hidden. Cards offer *Remind the agent*, *Open the item*, *Not an active branch* (for a radar finding) and *Acknowledge*; an acknowledged problem leaves Needs you until it needs a human step again (a proposed resolution, or a material change), and any decision counts as acknowledging it. The item page shows a **problem banner** on every tab while a problem exists, and *Open* lands on it. The radar reports **one problem per root cause**: a branch out of date with main is one problem, and pairs that only conflict because of it are left out; findings clear as soon as a branch stops being reported. When a problem needs more than a routine fix, an agent **proposes a resolution** (split, rescope, reorder or other, with a plan and a reason), and the owner approves it, asks for a different way with a note, or acknowledges it; each choice reaches the agent. Routine fixes (a rebase, removing an archival branch) need no proposal. A Help page, "Problems and what to do", explains each kind.
38. Project decisions off tickets, onto a project Decisions page (2026-11-20). In the Gameflow pilot, every ticket's Decisions section listed the project-wide decisions ("Prototypes for owner review", "Open with no commands", "Follow the Gameflow constitution"), so they cluttered every ticket and hid the few decisions made for it. So **a ticket shows only the decisions made for it: its own, its epic's and its labels'**, grouped and labelled by scope as before; an epic shows its own and its labels'. **Project-wide decisions are not listed there**; one line says how many also apply ("3 project decisions also apply · View") and links to the **project Decisions page**, where they are managed in one place: every project decision, with *Confirm*, *Supersede*, *Withdraw* and *+ Record a decision*, and a *Needs your review* filter (agents' unconfirmed ones). It opens from that line, the project switcher, Settings → Projects and Help. **An agent's new project-wide decision reaches the owner** as a Needs you card ("New project-wide decision by <agent>: <title>", with the text and the reason, *Confirm*, *Withdraw…*, *Acknowledge* and *Open*); it leaves Needs you once the owner confirms, withdraws or supersedes it, or acknowledges it (keeping it as an agent decision without confirming it). Item, epic and label decisions still don't reach Needs you. Agents' project decisions recorded before this change show once, as one grouped card per project. **Agents are unchanged:** `get_context` and `get_item` still include every decision in scope, project ones included, and no tool description changes.
39. Overlaps reach the owner only when they need the owner (2026-11-21; amends 36). See the section below.

## Product intent

A locally run Docker service coordinates AI agents' work: it gives them a stable MCP endpoint and is the enforced source of truth for work, dependencies, claims, decisions and review gates (owner decisions 18–19). A human supervises through a UI that shows the portfolio, dependencies, timing, agent activity, documents, and decisions that need review. Task state, agent execution state, review state, and delivery evidence must remain distinguishable.

## Core objects to validate

| Object | Purpose | Key relationships |
| --- | --- | --- |
| Project | Bounds a product or work area | Contains outcomes, work items, project-local artifacts, and an optional approval policy linked to its agent workflow documents. |
| Work item | Epic, Story, Task, or Bug | Optional epic; labels; explicit typed links; priority, status, dates, acceptance; lead claim by an agent rather than an assignee. |
| Dependency | Directed `blocks` edge between work items | Independent of hierarchy, ordering, and `relates`. |
| Checklist | Three short lists on one work item: Work (the agent's plan), Agent checks (its own verification), Human review (what the owner must verify) | Items are one or two sentences with state and history; they are not work items. A Work item that outgrows the checklist becomes its own Story or Task. |
| Agent run | One actual execution/session, including an optional delegated subagent record | References work item, plan step when relevant, and optional parent run; actor, timestamps, state, output. |
| Artifact | Locally stored document/file or a linked URL, commit, PR, test, build, deployment, screenshot, etc. | Project owner, version/source, and work item/run references. Local bytes stay in persistent storage. |
| Human review and handoff packet | An agent-written packet per review round, and an attributed owner decision per human review item | Approved or changes requested, with notes; findings become checklist items or bug tickets; decisions bind to that packet version. |
| Event | Immutable activity/provenance record | Actor, timestamp, object, action, prior/new values or evidence reference. |

## Initial workflow hypothesis

`Inbox → Planning → Ready → In progress → Review → Done`, with `Blocked` as a derived condition and `Canceled` as an explicit terminal outcome. Agents may produce planning artifacts for an item in Planning, but "ready to start" queries (A05) return only Ready items. The proposed design lets each project define which planning artifacts must be approved before Ready; see [UI design](UI_DESIGN.md). Review is used when the project's workflow requires or requests it; a no-approval project can move from In progress to Done after agent-reported completion. An item in Review can return to In progress after changes are requested. Run state (`working`, `needs input`, `finished`, `failed`, `stale`) is separate from work item status. The Planning status and the project-dependent approval choice are confirmed; the other statuses are still a proposal.

## MVP V1 boundary proposed for discussion

Build P0 work records, ticket plans, directional blockers, agent progress and subagent logs, project-configured approval, local review documents, an attention-focused host-only UI with a dependency graph and entered-date timeline, persistent Docker storage, and verified Codex/Claude/Orca MCP connectivity. Exercise V1 with disposable sample work and real local clients. Effort-based burn-down and velocity forecasts are P1; bulk automation, Scrum metrics, and full Jira scheme/plugin parity can wait until their need is demonstrated.

## Storage proposal to validate in design

For one local application host, use one service container with a SQLite database for structured work records and a project-scoped document directory, both inside a Docker named volume. The database and files are accessed only through the application. This avoids a MongoDB or separate database container for V1 while allowing project-level document deletion, backup, and restore. This is an implementation recommendation, not an owner-selected database contract. Docker volumes persist independently of container replacement. [Docker storage](https://docs.docker.com/engine/storage), [SQLite fit](https://www.sqlite.org/whentouse.html)

## Pilot after V1

Select a real project when V1 is usable and the owner has a suitable work stream. Decide then whether to start empty or import Jira records, and review any migration report before changing the project's source of truth. Active Jira work is not a prerequisite or a cutover target for V1.

## Owner decision 39 (2026-11-21): overlaps reach the owner only when they need the owner

Amends decision 36. The point of Docket is to keep agents implementing in parallel. Decision 36 asked the owner about every declared overlap: 7 so far in the Gameflow pilot, all same-file, 6 marked compatible. For any overlap, ask in order:

1. **Can they safely run at the same time?** Then they do.
2. **If not, or if it's unclear, would running them in order solve it?** Then Docket sequences them, and the waiting agent takes other work.
3. **Neither works, or it changes an approved design?** Then it reaches the owner, with the evidence and a recommendation.

The owner's correction shapes the design: "add-only" does **not** prevent merge conflicts. Two branches inserting at the same lines conflict, in Markdown, models or anything else, and Mergify doesn't resolve that. So there are two independent checks, and neither substitutes for the other. **Text:** do the actual lines collide? Only a git trial merge of real commits can answer. **Meaning:** do the changes collide semantically, even if git merges them cleanly? Declarations and agents answer this.

Altering an approved design always needs the owner, whether or not anything overlaps and in every setting: if an agent declares that its work changes an approved design, it comes to the owner and that work pauses while everything else continues. Only the owner can approve it or send it back.

Automatic outcomes are recorded as Docket, never as the owner, on both tickets, and the owner can overrule them with undo. Settings → Overlap handling (*Agents resolve*, the default; *Ask on shared data*; *Ask on every overlap*) applies globally and per project. Single-writer leases, Mergify requiring `build` and `e2e`, owner-recorded decisions and overlaps the owner already decided are unchanged. BUILD_SPEC §5.21 B46 has the rules.

## Owner decision 40 (2026-11-21): coordinators get what they need with far fewer tokens

Docket's core features are good; this decision makes them cheaper to use. The orchestrator should get the information it needs with as few tokens and as little time as possible. Evidence from the Gameflow pilot's session logs: three subagents started at about 132k tokens because they inherited their parent's conversation, where a fresh agent starts at 24–30k; a long-running coordinator carried about 160k of context and made 29,625 model calls, waiting by polling, so every check resent that context even when Docket's answer was tiny; Docket's tool definitions measured about 40k tokens.

1. **Wait without waking the model.** A waiting agent spends no model tokens until something relevant changes: a long-poll on the change feed, and an installed `docket-wait` script. No `sleep` loops.
2. **One compact coordinator snapshot.** `get_digest` replaces the usual round of reads, within about 1,000 tokens for a Gameflow-sized project, and with a cursor returns only what changed.
3. **Cheaper tool definitions.** At least 60% less than a client received before, with a contract test so it can't creep back, and without losing a rule agents depend on.
4. **Skills teach the cheap path.** Dispatch fresh, brief with the item ID, worktree, branch and how to report, load small context first, wait with `docket-wait`, restart from Docket past about 100k tokens of context, and keep subagent results short. Each skill has a line and token cap.
5. **Prove it.** A scripted coordinator scenario on a Gameflow-sized fixture reports the old path against the new one.

BUILD_SPEC §5.11 and MCP_SPEC §3 and §5.2 have the details.

## Owner decision 41 (2026-11-22): survive restarts, never miss a backup, and make Needs you truthful

Evidence from the Gameflow pilot. A restart marked every open run interrupted, so an update meant parking every agent by hand first. The 03:00 backup on Nov 21 never ran and recorded no error, and nothing caught it up. Needs you showed six Problems, none needing a person yet: three parked runs a coordinator owned, a radar conflict agents owned, and two misleading "unpushed work" rows. One said "1 commit not pushed" about a commit already on main, when what was left was 3 uncommitted files. The other told the owner to push work on an item the owner had canceled. The owner couldn't tell whether they were expected to commit that work, or what *Mark handled* did, and the sidebar badge showed a number that didn't match what they could act on.

1. **Runs survive a Docket restart.** Open runs stay open with their claim, workspace and `run_id`, and each lease runs at least `DOCKET_RESTART_GRACE_MINUTES` (default 15) from the restart. An agent's next call continues. One that never returns ends by normal lease expiry. Child runs have no lease, so they get the same window as a deadline: one that signals continues, and one still silent at the deadline ends as interrupted without affecting its parent. One `service.restarted` event, not one per run.
2. **Backups can't be silently missed.** At startup and on every scheduler wake, if the newest good backup is older than the last scheduled time, Docket catches up once, never concurrently, comparing the wall clock so sleep and clock jumps don't lose a night. A failed or overdue backup is an owner-visible Problem until the next success. Retention stays 14 days.
3. **Needs you only shows what needs the owner.** Parked-too-long and unpushed-work Problems go to the lead or coordinator first, and reach the owner only when no one can act or after the grace period, saying why.
4. **Unpushed work is true.** With a readable repository, Docket checks (read-only: no fetch, nothing written) whether HEAD is on a remote or in main, and reports commits and uncommitted changes separately. Without one it says the state is unverified. Canceled or deferred work is never something to push: the owner keeps it or lets it go. Docket never deletes a worktree or files itself.
5. **Actions say what they do.** *Mark handled* becomes *Keep for later* and *Safe to discard*. Each says what it does and doesn't do before it's confirmed (neither commits, pushes, saves or deletes anything), and can be undone.
6. **The badge equals what the owner can act on** on the page: same source, same count, none at 0.

BUILD_SPEC §5.3, §5.13, §5.16 and §5.22, MCP_SPEC §5.9 and UI_SPEC §6.1 have the details.

## Owner decision 42 (2026-11-22): status follows what agents are really doing

Evidence from the Gameflow pilot, Nov 20-22 (GF-370). GF-269 and GF-270 still read "parked, waiting on a mailbox" after the route was replaced and the flag enabled. GF-336 sat parked about 22 hours on a memory check that passed as soon as someone asked. GF-254, GF-239, GF-348, GF-349 and GF-280 expired to Ready while their producers were working, and GF-280 flipped between In progress and Ready about five times in an hour as small workers claimed and released it. A read-only `get_item` with a `run_id` also silently un-parked GF-374 and GF-376.

1. **Producers can reach Docket at launch,** with no credentials in shared or committed files and no change to user-level client config. Agent files and the coordinator skill give a copyable per-launch command. Where Docket can tell a session is working without it (commits on a silent run's branch), it says so.
2. **A named coordinator can update a run's status without its run ID:** current action, park reason, waiting-on, or resume. Only the run's recorded orchestrator or a coordinator the owner registered for the project may. It grants no claim, close, review or owner power, never counts as the run's own signal, and is shown as "updated by X".
3. **Docket notices drift.** After a park, new commits on the run's branches, updates on the item and cleared blockers show within a few minutes. When everything it waited on clears, it is ready to resume; anything less certain keeps the state and shows "activity since parked" to the coordinator. It reaches the owner only under decision 41's routing. A flag clears when the run or a coordinator speaks, and doesn't flap.
4. **A story has a stable producer across worker handoffs.** Workers under one producer hand it on without it returning to Ready or looking abandoned. One active lead and every seam, lease, design-review and overlap protection stay, and attribution stays per worker. A real release by the producer, or its hold running out, returns it to Ready.
5. **Only work resumes a parked run.** A read never resumes it, renews its lease or changes its park. `heartbeat` and other mutating calls naming the run do.

BUILD_SPEC §5.16 and §5.23, MCP_SPEC §5.4 and UI_SPEC §6.3 and §6.7b have the details.

## Owner decision 43 (2026-11-22): Overview replaces Needs you at `/`

Needs you did two jobs: it listed what requires the owner, and it was the only place to see how the work was going. The owner should be able to open Docket and answer three questions in about ten seconds: are agents making progress, is anything stuck, and do I need to do anything? `docs/design/overview-page.md` is the design.

1. **Overview is the home page,** for one project or All projects: four numbers (Completed, Agents, In flight, Needs you), the owner's actions, Health, completed per day, workload by epic, the Planning queue and Deferred reviews.
2. **The owner's actions come first** and nothing is lost: every card and action from Needs you works here. The badge stays decision 41's shared count, and equals the owner actions on the page. With none, the section says "Nothing needs you" and the badge disappears.
3. **Every number links** to the filtered view behind it. Long lists show a count and the top few, with *View all*.
4. **Agents are counted by story, at producer level, never as raw runs,** so one story handed between small workers counts once. The sidebar's Agents badge is the same number as the Overview card's *working*, for the same project; waiting stories aren't in it. The Agents page still lists individual runs and says so. Problems agents own stay collapsed to one line.
5. **The time window** is 24 hours, 7 days or 30 days, 7 days by default, remembered per browser, and compared with the preceding window of the same length.
6. **No token use and no estimated metric,** because clients don't report tokens to Docket.
7. **Insights have a place but aren't built.** Radar insights come later as proposals, and the page shows no empty placeholder for them.

## Owner decision 44 (2026-11-22): a coordinator can park a run for a limited time

Decision 42 deliberately stopped a coordinator from parking an open run, because parking suspends the claim timer and a mistaken park could hold a dead run's ticket forever. In practice, when a producer stops to wait and goes quiet, its coordinator has to keep it alive or watch its lease, which spends tokens and misstates what is happening. A park that always ends by itself removes that risk.

1. **A named coordinator can park an item's live lead run for a stated time,** with a reason and what it waits on, through `update_run_status`. The authority is decision 42's: the run's recorded orchestrator, or a coordinator the owner registered for the project. It grants no claim, close, review or owner power, and never speaks as the run.
2. **The limits are 4 hours per park and 24 hours in total since the run's last own signal.** A request over a limit is refused with a clear error, never shortened. A coordinator can renew within the limits or end the park early. Docket records and shows who parked it and until when.
3. **A coordinator's park always ends.** At the deadline the run returns to open on a short lease, the restart grace. A live agent continues, and a dead one loses its claim through the normal lease expiry. The deadline survives a restart.
4. **The run's own park stays unlimited.** Its own later `park_run` replaces the time limit, a real write by it resumes it, and a read never does. A coordinator can't put a time limit on a park the run set itself.
5. **The coordinator hears about an expired park** through the feed and the digest. It reaches the owner only under decision 41's routing.
6. **Other protections are unchanged.** Part leases keep their own clock and aren't extended by a park, so a part another item needs still comes free on time. Overlaps, holds, producer holds, activity flags and `resume_ready` work as for any parked run.

BUILD_SPEC §5.25, MCP_SPEC §5.4, UI_SPEC §6.3 and spec FR-206–FR-210 have the details.

## Owner decision 45 (2026-11-23): a parked story's wait is visible and has a next step

In the Gameflow pilot two stories sat parked for about five hours on prerequisites in Planning. Nobody owned the prerequisite's next step, and one of them said it needed an owner decision that nobody had asked for. Every alert stayed quiet: `parked_too_long` waits a day, `resume_ready` and `resume_unattended` fire only after the blocker clears, and `run.activity` reports motion, not its absence. The owner asked for the smallest improvement that would have exposed it.

1. **Every parked lead has a wait card,** derived from what Docket already stores: what it waits for and what clears it, how long since this run **first** parked on it (a short resume and re-park doesn't reset the clock), who owns the next action, and one exact sentence on how the same run resumes. It appears in the `park_run` result, `get_digest`, `get_context` on the parked item **and on its blocker**, and the item page, inside the token budgets.
2. **The next action's owner** is the blocker's live lead, else the waiting run's recorded orchestrator, else a project coordinator, else the owner. Docket follows an uncleared blocker chain to the item that can actually move, with a bounded depth, and survives a cycle.
3. **Two advisory flags,** checked every two minutes with no git. `wait_no_next_step`: an uncleared blocker has no live lead, no open question, no pending packet or owner action, and no real activity for 15 minutes. `wait_owner_unasked`: the run waits on a person, or its park reason or a direct blocker's text says an owner decision is pending, and nothing has been put to the owner. The match is narrow: text citing a recorded decision doesn't count. Each flag raises once and clears when its condition ends.
4. **They go to whoever can act.** Agents first, through `get_digest`, `get_context` and one `run.wait_flagged` event that wakes `docket-wait`. They reach Needs you and the badge only under decision 41's routing, saying why. An unasked decision goes to the coordinator **to ask**, because the owner can't answer a question that doesn't exist.
5. **When every named blocker clears,** one `run.resume_ready` event names the same run, label, client, dispatch and the resume instruction, and the digest shows it first. **Docket can't push into an agent's session,** so the coordinator relays it. The 30-minute `resume_unattended` fallback stays.
6. **A blocker added after work started gets a prompt.** When a named blocker was linked after this run claimed the item, the card says to confirm it holds the whole story and, if only part is held, to split that part out and let the rest proceed. It is one line of advice, with no new link type, flag, event or gate.
7. **Advisory only.** Nothing here blocks a claim, a status change, a queue or a delivery, and `satisfied_when` doesn't change.

`docs/design/wait-and-backlog-followups.md` records what this leaves open, proposed and not built. Which kind of dependency a link is stays an open question until the types are designed with the owner.

BUILD_SPEC §5.26, MCP_SPEC §4 and §5.4, UI_SPEC §6.3.2 and spec FR-211–FR-216 have the details.

## Owner decision 46 (2026-11-23): wake the right session when the owner changes a ticket

The owner answers a question in Docket, but the agent sees it only on its next Docket call. The last 7 answered questions took 1 to 80 minutes to be picked up (median 8), and the owner has had to open the session and tell it to check. Neither Claude Code nor Codex offers a usable way for Docket to push into a running session. Orca messages do wake idle sessions, and Docket's container can't call the host's `orca` CLI, so a small host process bridges them.

1. **`docket-relay` watches the change feed from the host,** at no token cost, and survives Docket restarts. It needs no server change.
2. **It reacts to owner-side changes that can affect the live lead:** edits to the title, description, outcome or acceptance; status changes, cancel and archive; decisions published or confirmed on the item; owner notes; answered questions; review, overlap and hold decisions; blocker links added or removed; and `run.resume_ready`. Agent events and housekeeping are ignored, so it can't create a message loop. A ticket with no live lead gets no message.
3. **A burst is one wake-up.** Edits wait for 60 seconds of quiet, and at most 2 minutes after the first change. An answered question goes immediately and carries whatever is waiting on that ticket.
4. **The message is a pointer, never the content.** It names the ticket and the kinds of change. The agent reads the rest from Docket, which stays the source of truth and keeps `read_by_agent_at` honest. The relay never resumes, parks, claims, changes status or calls `get_item`.
5. **It reaches the implementer, or says who should.** A live Orca dispatch is the implementer. Otherwise its coordinator is told, naming the implementer. A stored session ID that may be a coordinator is never presented as the implementer. With nobody to tell, it's recorded as undelivered, and Needs you isn't touched.
6. **Honest wording.** Owner-kind events can also come from an agent using the owner API, and Docket can't always tell them apart, so the message says "updated from the owner side".
7. **Reliable and local.** A durable cursor and ledger outside the repo, no replay on first run, catch-up within 24 hours, no duplicates across restarts, bounded retries, a rate limit per session, one instance, and a status command with no message content.

BUILD_SPEC §5.27, spec FR-217–FR-223, Help (Questions and notes) and `tools/docket-relay/README.md` have the details.

## Validation scenarios for the next pass

- Two agents try to claim/update one Story simultaneously; only one takes ownership, and the other receives current state and a clear conflict.
- A parent agent delegates two child runs. One succeeds, one stops heartbeating. The reviewer sees both outcomes and the parent remains unresolved.
- A lead agent posts a three-step ticket plan, starts the second step, reports a subagent's completed contribution in a short log, then changes the final step. The owner sees planned, current, completed, and changed work without extra tickets.
- Story B is blocked by Story A in another project. A moves to Done; B becomes ready and the graph/timeline update without treating mere parentage as a blocker.
- An agent uploads a document for review, then revises it after requested changes. Approval of the old version does not approve the new one.
- A PR merges and CI passes, but the required owner walkthrough is still pending. The work item remains in Review and the dashboard shows the pending gate.
- In a project configured without owner approval, an agent completes the declared acceptance and reports Done. The UI shows agent completion accurately without inventing an owner approval.
- An agent updates a planned date and estimates a ticket at five points. The timeline labels the entered date; the burn-down uses the effort value only after enough completed work exists to show a meaningful rate.
- A project with local Markdown reviews is deleted through the UI. Its work records and files are removed together, while retained backups follow the documented backup policy.
- Docker restarts during an active run; task data persists, the run stays open and its agent continues with the same `run_id` (decision 41). If the agent never returns, its lease ends it as interrupted, never falsely finished.
